01 — Mechanism

One token, then the next

A model doesn't know an answer up front. Given the tokens so far, it scores every possible next token, samples one, appends it to the sequence, and repeats — until a stop condition ends the loop. No mathematics required to use it well, but that loop explains almost everything downstream: why output can drift, why the same prompt can end two different ways, and why grounding the loop in real context changes the result.

02 — Constraint

Everything shares one window

Text is broken into tokens before the model ever sees it, and every model has a fixed context window — a hard ceiling on how many tokens of instructions, history, retrieved files, and response can exist at once. System prompt, chat history, @-mentioned files, and the model's own output all draw from that same finite budget. When it fills, something has to give — usually the oldest turns first. This is the real reason agent and tool design revolves around what to include, not just what to ask.

03 — Input design

Instructions are layered, not flat

A response is shaped by layers stacked before your question ever arrives: a system prompt that sets persistent role and rules, optional few-shot examples that demonstrate the pattern you want, and finally the user prompt itself. Clarity compounds top to bottom — a vague ask on a solid foundation still wanders; a precise ask on a clear foundation lands close on the first try.

Vague user prompt

"Fix the bug."

Which bug, which file, which behavior? The model guesses, and the guess is often wrong.

Specific user prompt

"parseOrder() at line 42 throws when shippingAddress is missing — add a guard and return a 400."

One target, one testable fix, on the first pass.

04 — Capability & risk

Fluent is not the same as correct

Generative models are genuinely capable — drafting, summarizing, explaining unfamiliar code, completing a pattern from a handful of examples. They are just as capable of stating a wrong answer in the same confident voice as a right one. Three properties explain most of the friction teams hit in practice.

Hallucination

A fluent, confident answer with no signal to distinguish it from a fluent, confident wrong answer.

Knowledge cutoff

Anything that changed after training — a new API, a rewritten module — sits in the model's blind spot.

Non-determinism

The same input can sample a different path through the same distribution — twice is not proof of consistency.

05 — Mental model

Software you can predict, and software you can't

Traditional code is deterministic: the same input walks the same branches to the same output, every time, and a unit test can prove it. A generative model replaces that branch tree with a probability distribution — the same input produces a distribution of plausible outputs, and which one you get can vary. That single difference is why AI-assisted engineering needs verification and traceability built into the workflow, not bolted on after.

07 — Shared vocabulary

Nine terms the rest of this course assumes

Defined once here, used without re-explanation from Module 2 onward.

LLM

A large language model — trained to predict the next token in a sequence, at massive scale.

Context window

The fixed maximum number of tokens a model can hold at once — instructions, history, and response all share it.

Context engineering

Deliberately choosing what enters the window — which files, docs, and history — so the model reasons over the right facts.

Agent

A model given a goal, a toolset, and permission to plan, act, and check in a loop, rather than a single reply.

Subagent

A focused agent delegated one narrow piece of work in its own isolated context, then handed back a result.

Skill

A packaged, reusable capability an agent can invoke for a specific kind of task, versioned like code.

Orchestration

The pattern that coordinates multiple agents or subagents — sequencing, parallel delegation, and result hand-off.

MCP

Model Context Protocol — a standard way to connect an agent to repositories, docs, tickets, and APIs as live tools.

Spec-driven development

Treating a structured, versioned specification as the source of truth an agent implements against, not a one-off prompt.
