01 — What you're building

Five agents, five artifacts, one run folder

Each agent is a versioned definition in the repo (Module 10 anatomy). Each stage writes a named artifact plus a handoff envelope, and the next stage reads only those files. In this lab you are the orchestrator: you run the stages in order following PIPELINE.md. Module 19 moves that into CI.

Repository layout

requirement-to-test/
├── .cursor/
│   ├── rules/pipeline-handoff.mdc   # envelope, AC-IDs, no self-approval
│   └── agents/                      # 5 role definitions
├── requirements/REQ-2481.md         # input
├── specs/openapi.yaml               # target API contract
├── tests/                           # ONLY Generator writes here
├── runs/req-2481-run-01/            # 01…05 + trace + log
└── PIPELINE.md                      # order, budgets, stop rules

PIPELINE.md: stop rules

# Pipeline: requirement-to-test v1.0.0
Stage 1 FAIL        → stop, gaps to owner
Any NEEDS_HUMAN     → stop and ask
Correction rounds → max 2, then escalate
Budget per run    → 20 min · 400k tokens
Exceeded          → halt (fail-safe)

# handoff envelope (every stage)
run_id · stage · status · input_refs

02 — Part A · Stage 1 · 20 min

The Validator is the cheapest place for the pipeline to fail

Before any tokens go into generation, check every acceptance criterion: is it complete, unambiguous, and observable through the API? The Validator flags gaps as questions for the owner. It never fills a gap by making up a requirement.

requirements/REQ-2481.md

REQ-2481: Order cancellation

As a customer, I want to cancel an order before it ships so that I am not charged.

  • AC-1Cancel own order while PENDING or PAID → 200, status CANCELLED
  • AC-2Cancel a SHIPPED order → 409 ORDER_ALREADY_SHIPPED
  • AC-3Cannot cancel another customer's order → 403
  • AC-4Cancellation of a PAID order triggers a refund⚠ deliberately vague: how is the refund observable via the API?

01_validated_requirement.md (excerpt)

Classification per AC

  • AC-1TESTABLE: 200 + status observable
  • AC-2TESTABLE: 409 + error.code in spec
  • AC-3TESTABLE: 403 defined; needs 2nd customer
  • AC-4NEEDS_CLARIFICATIONQ1: Assert a refund record via GET /refunds?order_id={id}, and within what time?
Lab step

Run the validator. Then act as the requirement owner and answer Q1 (e.g. "yes, a refund record with status PENDING appears immediately"). Update REQ-2481.md and re-run until the status is PASS. The run log should now have two lines for stage 1.

03 — Part A · Stage 2 · 20 min

The Builder decides what to test and in what order, not how

The Builder turns validated ACs into an ordered test sequence with no implementation detail: setup, action and expected result for each scenario, and every scenario tagged with its AC-IDs. It reads only the validated artifact, never the original requirement, and never names a framework.

02_test_sequence.json (one scenario)

{
  "id": "SEQ-2",
  "ac_ids": ["AC-2"],
  "title": "Cancel SHIPPED order is rejected",
  "setup": ["customer_a authenticated",
            "order O2 owned by customer_a, SHIPPED"],
  "action": "POST /orders/{O2}/cancel as customer_a",
  "expect": ["HTTP 409",
             "body.error.code == ORDER_ALREADY_SHIPPED",
             "order O2 status unchanged"],
  "evidence": "openapi.yaml#/…/cancel/post/responses/409"
}

What a good sequence looks like

  • Coverage: ≥ 1 scenario per AC, plus negative cases for error ACs
  • Independence: each scenario sets up its own state
  • Data: named fixtures (customer_a, paid_order), no magic values
  • Observability: every expect is something the API returns (cite the spec)
  • Must not: add scenarios without an AC-ID, name libraries, or write code
End of Part A

You should have 01_validated_requirement.md and 02_test_sequence.json, both status: PASS, and at least two stage lines in run_log.jsonl. 15-minute break.

04 — Part B · Stage 3 · 25 min

One writer, one folder, a marker on every test

The Generator is the only stage with write access, and only to tests/. It follows the repo's existing test conventions and conftest.py fixtures. The most important thing it does is put traceability in the code itself: every test names its scenario and AC-IDs, so any result can be traced back to the requirement.

tests/test_req_2481_order_cancellation.py

pytestmark = pytest.mark.req("REQ-2481")

@pytest.mark.ac("AC-2")
@pytest.mark.seq("SEQ-2")
def test_cancel_shipped_order_rejected(
        api, customer_a, make_order):
    """SEQ-2 / AC-2: SHIPPED → 409, status unchanged."""
    order = make_order(owner=customer_a, status="SHIPPED")
    resp = api.as_user(customer_a).post(
        f"/orders/{order.id}/cancel")

    assert resp.status_code == 409
    assert resp.json()["error"]["code"] == "ORDER_ALREADY_SHIPPED"
    assert api.as_user(customer_a).get(
        f"/orders/{order.id}").json()["status"] == "SHIPPED"

pytest.ini: register the markers

[pytest]
markers =
    req(id): source requirement ID
    ac(id):  acceptance criterion ID
    seq(id): test sequence scenario ID

Generator discipline

  • One test per scenario (or parametrize for variants): SEQ ↔ test is 1:1
  • AC/SEQ IDs as markers (for machines) and in docstrings (for people)
  • Reuse fixtures; add new ones only to conftest.py
  • No secrets or hard-coded URLs; read from env/config (Module 14)
  • Assert exactly the expect list, no more and no less
  • Never marks its own work as approved

05 — Part B · Stage 4 · 20 min

Well-written tests can still test the wrong thing

Tests can have the wrong path, a status code the spec never declares, a field that doesn't exist, or an assertion the API can't satisfy. The API Validator checks the tests statically against openapi.yaml, then runs them against the sandbox, and classifies every failure before sending anything back.

04_api_validation_report.md (excerpt)

## Execution (sandbox, 2026-09-23T10:42Z)
6 collected · 5 passed · 1 failed

FAILED test_cannot_cancel_other_customers_order
  expected 403, got 404
  Classification: PRODUCT_DEFECT?
  Spec declares 403 (openapi.yaml#/…/403)
  Action: flagged to Reviewer + owner;
          test NOT modified.
Watch for

The validator did not "fix" the test to match the API. Changing the assertion to 404 would turn the suite green and hide a real spec violation. That refusal is the behaviour you want. The failing test is what makes the defect visible.

06 — Part B · Stage 5 · 15 min

The Reviewer judges against the source, not the story

The Reviewer gets a fresh context: the original requirement, the tests, and the API validation report. It does not see the Generator's reasoning or the chat history. That way it can catch drift that built up across stages 1–3 instead of inheriting it.

APPROVE

All ACs covered, tests correct and maintainable, open defects acknowledged. → human approves the commit.

REQUEST_CHANGES

Specific, actionable findings, each tied to an AC-ID or test. → back to the Generator (bounded).

ESCALATE

Product defect, requirement conflict, or out-of-scope concern. → human / owner decides.

Reviewer checklist (put it in the agent definition)

  • Coverage: every AC in the original requirement has a test with a matching ac marker
  • Correctness: assertions match the AC wording, not just the sequence
  • Negative paths assert the error and the unchanged state
  • Independence: no order-dependent tests or shared mutable state
  • Hygiene: no secrets, hard-coded URLs, sleeps or disabled asserts
  • Honesty: failures reported, never xfail-ed without a defect link

05_review_signoff.md

Verdict: ESCALATE (approve tests; 1 open defect)
Reviewer: reviewer@1.0.0 · req-2481-run-01 · attempt 1

Coverage vs ORIGINAL requirement:
  AC-1 ✔ (2 tests) · AC-2 ✔ · AC-3 ✘ · AC-4 ✔

07 — Part B · End-to-end run · 15 min

Start anywhere in the chain and walk to every other point

"Traced back to its source requirement" means anyone can go from a requirement to its tests and results, or from a failing test back to the AC it protects, without asking whoever built it. The markers, the sequence JSON and the results together make that possible.

08 — Part B · Deliverable and peer review · 15 min

An executable, validated suite, traced to its requirement, then someone else tries to break it

The lab is done when another pair can run your pipeline themselves, on a second requirement, and it still holds up. Reading the files isn't enough for them to judge that.

Deliverable checklist

  • Five agent definitions under version control: role, inputs, tools, "must NOT", outputs
  • PIPELINE.md + the shared pipeline-handoff.mdc rule
  • One complete run folder: 01–05 + traceability.md + run_log.jsonl
  • Tests in tests/ that collect and run, with req/ac/seq markers
  • Human approval recorded in the commit or PR (run ID + reviewer verdict)

09 — What usually goes wrong

Six pitfalls you'll probably hit, and how to fix each

Validator "helps"

It rewrites vague ACs; tests pass but miss what the owner meant.

"Must NOT invent" guardrail; emit clarification questions.

AC-IDs drift

Renumbered or merged IDs; the traceability table doesn't line up.

Handoff rule: carry AC-IDs forward unchanged.

Writes outside tests/

Edited spec, or fixtures added under src/.

Scope write permission; Reviewer checks diff paths.

Tests bent to a bug

Suite goes green; the defect disappears from view.

API Validator classifies failures; product defects never get "fixed" in tests.

Reviewer shares context

It approves everything.

Fresh subagent/chat; pass only original req + tests + report.

Endless "try again"

Many attempts, rising token cost.

Count rounds in run_log.jsonl; cap at 2, then escalate.

Stretch goals

Parallel fan-out: split the Generator per endpoint and add a merge step, then compare time and tokens in the run log. Router: send UI requirements down a Playwright path instead of PyTest. Reuse: run the unchanged pipeline on a new requirement to check the agents aren't over-fitted to REQ-2481.

10 — Before Module 17

Carry these four ideas forward

01

Validate before you generate. Unclear criteria stop the run as questions for the owner. They never get filled in by guesswork.

02

Each stage reads only the previous stage's files and writes one named artifact. Only the Generator writes code, and only in tests/.

03

Classify failures before routing them. A test that exposes a real bug stays failing, and an independent Reviewer judges against the original requirement.

04

AC-IDs are the traceability spine: requirement → AC → scenario → test → result, in both directions, backed by run_log.jsonl.

Why should the Validator return NEEDS_HUMAN for AC-4 instead of assuming how a refund is observed?

Filling the gap would be inventing a requirement, and the tests would then check the agent's guess instead of the owner's intent. Surfacing the ambiguity at stage 1 is also the cheapest point to do it.

Why does the Builder read the validated requirement while the Reviewer reads the original?

The Builder should work from the checked, clarified artifact so each stage stays isolated. The Reviewer judges against the source of truth, so any drift introduced by stages 1–3 gets caught instead of passed along.

A generated test gets 404 where the spec says 403. Who changes what?

Nobody changes the assertion. The API Validator classifies it as a product defect, the Reviewer escalates, and the owner raises a defect. The test keeps failing until the API is fixed.

Only the Generator's output changed. Which stages re-run?

Stages 3–5 (Generator, API Validator, Reviewer). Stages 1–2 are upstream and unaffected, so their artifacts are reused. Module 18 automates this downstream-rerun pattern.

What concretely makes the suite "traced back to its source requirement"?

Every test carries req/ac/seq markers, traceability.md maps each AC to scenarios, tests and results in both directions, and the run folder plus run_log.jsonl show how each artifact was produced.
