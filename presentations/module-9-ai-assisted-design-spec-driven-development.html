01 — The durable artifact

A spec outlives the chat that wrote it

A prompt is read once and forgotten when the session ends. A spec is a file in the repo — reviewed, versioned, and re-read by every agent and every teammate that touches the feature afterward, not just the one that opened the first chat.

02 — Change management

Every clause traces to code and to a test

Spec-to-code and spec-to-test traceability means each requirement clause has an ID, and every module and test case implementing it references that ID back. When a clause changes under versioning, everything traced to it is flagged automatically — nothing drifts silently.

03 — Three approaches, compared

Rigor is a dial, not a switch

Vibe-coding produces nothing durable. Prompt-driven development produces code from a single pass with nothing to verify it against. Spec-Driven Development closes the loop — a reviewed spec feeds a plan, a plan is approved before code is written, and the result traces back to where it started.

04 — Requirements to plan

Explore the repo before you plan the change

Cursor's plan-mode rhythm — explore, plan, review, implement — applies directly to requirements work: the agent reads the existing codebase and requirements together, drafts an implementation plan grounded in what's actually there, and waits for approval before touching code.

05 — Design artifacts

One requirements pass, two durable artifacts

Given requirements and repo context, Cursor can draft both a component/data-flow architecture diagram and an API/interface contract in the same pass — two artifacts that get reviewed and versioned alongside the spec, not regenerated from scratch on every implementation task.

06 — SRS → SDS, with decisions logged

Business requirements become system design, on the record

Translating an SRS into an SDS with AI assistance is a structured pass, not a rewrite from memory — and every non-obvious design choice along the way gets captured as an Architecture Decision Record, so the "why" survives even after the "what" ships.

07 — Subtopic: what belongs in a spec

Acceptance criteria are testable clauses, not prose

The line between a spec and a prompt is testability. A prompt says "add rate limiting." A spec clause says exactly what "done" means — Given/When/Then criteria a test can check mechanically — and nothing gets implemented until a human approves that clause.
