01 — What changes since Lab 3

You stop being the gate

The agents from Lab 3 stay as they are. What's new is a small control plane around them: a script that evaluates each gate from the artifact, a script that decides what happens next, and hooks that check actions inside the agents. The agent that orchestrates follows next_step.py; it doesn't get to decide on its own that a stage is "good enough".

Bring from Module 16–17

  • The five Lab 3 agents, PIPELINE.md and the handoff rule
  • gates.yaml v1.0.0 and the gate-log schema (Lab 17.1, 17.3)
  • .cursor/hooks.json with the Module 17 hook scripts
  • runs/req-2481-run-01/ as the baseline to compare with
  • Your Lab 17.4 automation-gap table, if you did it

Build today

  • scripts/gate.py: one gate in, one logged verdict out
  • scripts/next_step.py: guards, routing, rerun plan
  • Validation hooks wired to the engineering checks you choose
  • A decision packet and a hash-bound approval before commit
  • A fresh run, req-2481-run-02, with its complete trail
Names

Script and file names on these slides are suggestions. If your Module 17 work used different names, keep yours. What matters is that each decision is made by code, from the artifact, and logged.

02 — Activity 1 · Automated gates

Put a gate between every hand-off

G1 and G2 carry over from Module 17. The work today is on the three gates between the generator, the validator and the reviewer, where most failures happen and where a wrong route costs the most.

  G4:

    checks: {L3: [run_suite, classify_failures]}

      ENVIRONMENT: {rerun_stage: 1, then: NEEDS_HUMAN}
  G5:

    accept: [APPROVE, ESCALATE]
    on_fail: {route: test-generator, mode: patch}
    then: HITL_commit

scripts/gate.py (sketch)

def evaluate(gate_id, run, cfg):
    try:
        v = _ladder(cfg.gates[gate_id], run)
    except Exception as e:   # checker broke
        v = Verdict("NEEDS_HUMAN",
                    error=repr(e))  # never PASS
    log_verdict(v, gate_id, run,
                cfg.version)        # always
    return v

def _ladder(gate, run):
    done = []
    for level in ("L1", "L2", "L3", "L4"):
        for name in gate.checks.get(level, []):
            r = CHECKS[name](run)  # the artifact,
            done.append(r)         # not the claim
            if r.status == "FAIL":
                return Verdict("FAIL", done,
                    route=gate.route_for(r))
    return Verdict("PASS", done)
Rule

The gate re-derives everything from the artifact. An envelope that says "status": "PASS" is a claim to check, not a verdict.

Checkpoint

Run gate.py G3 against run 01's test file and get a logged verdict. Then rename gates.yaml and run it again: you should get NEEDS_HUMAN with the error in the log, not PASS.

03 — Activity 2 · Correction loop

A FAIL goes back with findings, not "try again"

When a gate fails, next_step.py first checks whether another round is allowed and worthwhile. Only then does it write a findings file and re-invoke the owning stage, telling it to patch the existing artifact rather than start over.

runs/…/findings/G5-r2.json · the structured feedback

{
  "gate": "G5", "round": 2,
  "route_to": "test-generator", "mode": "patch",
  "artifact": "tests/test_cancel_order.py@c07e",
  "findings": [{
    "test": "test_cancel_shipped_order_rejected",
    "ac": "AC-3",
    "criterion": "rejected cancel leaves order unchanged",
    "observed": "asserts 409 only",
    "expected": "also GET order → still SHIPPED",
    "evidence": "05_review_signoff.md#F-1"
  }],
  "do_not_change": ["test_cancel_creates_refund",
                    "AC markers", "pytest.ini"],
  "previous_attempts": [
    "r1 (G3): added missing AC marker"]
}

scripts/next_step.py · after a FAIL (sketch)

def after_fail(v, state, cfg):
    state.rounds += 1          # shared counter
    prev = state.history.get(v.gate)
    if state.rounds > cfg.max_rounds:
        return escalate("round limit", v)
    if prev and v.hash == prev.hash:
        return escalate("no progress", v)
    if prev and len(v.findings) >= \
            len(prev.findings):
        return escalate("not converging", v)
    if weakened(v, prev):   # asserts, skips
        return escalate("invariant", v)
    write_findings(v, state)
    return retry(v.route, mode="patch")
Why patch

Regenerating the whole file throws away tests that already passed review. do_not_change and previous_attempts stop the generator from undoing earlier fixes.

What

Observed vs expected

The exact assertion that's wrong, and what the spec or reviewer expects instead.

Where

Test + AC + evidence

A test name, an AC-ID and a link to the report line, so the fix is targeted.

Keep

do_not_change

Tests and files that already passed. Changing them is out of scope for this round.

History

previous_attempts

One line per earlier round, so the agent doesn't repeat a fix that already failed.

04 — Activity 3 · Downstream reruns

Rerun what depends on the change, and nothing else

The Reads column in PIPELINE.md says which artifacts each stage consumes. Each envelope records the hash of its inputs, so next_step.py can tell which stages now have different inputs. Those rerun; the rest are reused as they are.

Why not just rerun everything?

It costs more, but that's the smaller problem. Rerunning stage 2 regenerates a sequence that was already checked, and it can come back different. Then tests and the review have to be redone against something nobody asked to change.

Reuse is safe only when the input hash matches. That turns the question into a mechanical check, the same way a build system decides what to recompile.

05 — Activity 4 · Validation hooks

Catch problems on the edit, not at the gate

A gate finds a missing marker after the whole stage is done. A hook can find it the moment the file is saved, while the agent is still working. Pick a few engineering checks that are cheap and deterministic, and run them from hooks. The gate still makes the final decision.

Per action · inside the agent

Hook

Format and lint each edited test, check AC markers, keep writes inside tests/, block risky commands.

Fast feedback

Per stage · between agents

Gate

Collect-only, schema, classification of failures, reviewer verdict. Judges the whole artifact once it's finished.

after-edit-validate.sh (outline)

#!/usr/bin/env bash
# afterFileEdit observes: validate + log
file=$(python3 scripts/hook_field.py file_path) \
  || exit 0              # bad payload: log only
case "$file" in
  */tests/*.py)
    ruff format -q "$file"
    ruff check -q "$file" || log lint
    python3 scripts/check_markers.py "$file" \
      || log missing_ac_marker ;;
  *gates.yaml|*pytest.ini|*.cursor/*)
    log OUT_OF_SCOPE ;;   # G3 will FAIL
esac

Hook event names, payload fields and what a hook's output can do have changed between Cursor releases. 06 — Activity 5 · Human approval checkpoint

One person signs off, and the approval is tied to what they saw

After G5 returns APPROVE or ESCALATE, the pipeline stops and builds a decision packet. A named approver decides. The approval is logged with the artifact hash, so if anything changes afterwards the approval no longer counts.

decision_packet.md · req-2481-run-02

Decision needed: APPROVE / REJECT / REQUEST CHANGES

  • trail G1 ✔ G2 ✔ G3 ✔ (round 1) G4 ✔ flagged · G5 REQUEST_CHANGES → round 2 → G5 ESCALATE
  • coverage AC-1 … AC-4 all covered · 6 tests
  • open defect DEF-5520 · spec says 403, API returns 404 · test kept failing on purposePRODUCT_DEFECT · not retried

08 — Deliverable

A bounded pipeline with a trail anyone can follow

The deliverable is more than a green run. Someone who wasn't in the room should be able to open the run folder and answer: what was checked, what failed, who fixed it, what was rerun, and who approved the result, and why.

suggested layout

requirement-to-test/
├─ PIPELINE.md          # Reads column → reruns
├─ gates.yaml           # v1.1.0 · criteria + bounds
├─ .cursor/hooks.json   # + hooks/*.sh
├─ scripts/
│  ├─ gate.py           # gate → logged verdict
│  ├─ next_step.py      # guards · routing · reruns
│  └─ packet.py         # decision packet
└─ runs/req-2481-run-02/
   ├─ 01_… 05_…          # artifacts + envelopes
   ├─ findings/          # G3-r1.json, G5-r2.json
   ├─ gate_log.jsonl     # gate trail
   ├─ results.xml        # validation evidence
   ├─ traceability.md    # AC ↔ test ↔ result
   └─ decision_packet.md # + approval trail

Definition of done

  • Every gate decision in gate_log.jsonl with version, round, hash, checks, route and decided_by
  • At least one real correction round, with its findings file
  • A rerun plan showing which stages were reused and which were rerun
  • Hook decisions in hook_log.jsonl, including one deny
  • The fail-safe drill: a broken config gives NEEDS_HUMAN, never PASS
  • results.xml and traceability.md as validation evidence
  • An approval entry bound to the final hash, then the commit

Peer review: try to break the other team's pipeline

  1. Remove an AC markerG3 should FAIL, use round 1 and write a findings file that names the test.
  2. Break gates.yamlExpect NEEDS_HUMAN with the error logged. A PASS here is an automatic fail of the review.
  3. Make the generator return the same file twiceThe no-progress guard should escalate before the round limit.
  4. Run git commit without an approvalcommit-guard should deny it and log the denial.
  5. Check a reuse decisionCompare the hashes of 01 and 02 across rounds. They should match.
  6. Ask the log a question"Why did G4 pass with a failing test?" The answer should be in the log, not in someone's memory.

09 — Pitfalls seen in this lab

Six ways a self-correcting pipeline goes wrong

The gate trusts the envelope

G3 PASS, but pytest --collect-only fails.

Every check reads the artifact. The envelope's status is only a claim.

A product defect gets "fixed"

The generator changes the 403 assertion to 404 so the test passes.

PRODUCT_DEFECT is flagged and passed through. It never goes back to the generator.

A counter per gate

Two rounds at G3, then two more at G5: four rounds in total.

Keep one counter in the run state, shared by G3, G4 and G5.

Rerun everything

A reviewed sequence comes back with different scenario names.

Use the Reads column and input hashes. Reuse any stage whose inputs didn't change.

A crash counts as PASS

The log has an error and "decision": "PASS" on the same line.

Wrap every gate. Any exception gives NEEDS_HUMAN.

The approval floats

Tests change after sign-off and still get committed.

Store the hash with the approval. commit-guard checks that it matches.

10 — Before Module 19

Carry these five ideas forward

01

Agents do the work; scripts make the decisions. Gate verdicts and next steps come from code reading artifacts, so they're repeatable.

02

A FAIL returns to its owner as structured findings with a do_not_change list, and the owner patches instead of regenerating.

03

One shared round counter plus progress guards. Rounds left is a limit, not a target.

04

Reruns follow the Reads column and input hashes. The changed stage is re-gated, later stages rerun, earlier ones are reused.

05

A named human approves a short decision packet, the approval is tied to the artifact hash, and a hook enforces it before commit.

Why does the gate re-check the artifact instead of reading the agent's status?

The status is the agent describing its own work. A gate exists to check that claim independently: collect the tests, parse the markers, read results.xml.

G4 sees one failing test classified PRODUCT_DEFECT. What happens?

G4 passes with the failure flagged. The test stays as it is, and the defect goes to the reviewer and the decision packet. Sending it back to the generator would push it to weaken a correct test.

The reviewer requests changes to the tests. Which stages rerun?

The Test Generator patches the file and G3 re-gates it. The API Validator and the Reviewer rerun because they read 03. Stages 1 and 2 are reused because their input hashes didn't change.

Round 2 of 2 has been used and G3 fails again. What does next_step.py do?

It escalates to a human with the history of every round. It doesn't start a round 3.

Where should a check like "every test has an AC marker" live: hook, gate, or both?

Both. The hook gives the agent feedback while it's editing. The gate is still the decision point, because a hook can be missed or misconfigured and the verdict has to come from the finished artifact.

Why bind the approval to an artifact hash?

Otherwise an approval of one version can be used to commit a different one. With the hash, any later change voids the approval and needs a new decision.
