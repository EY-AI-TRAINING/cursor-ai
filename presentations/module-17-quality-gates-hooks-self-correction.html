01 — Four mechanisms, four different questions

A control layer on top of the Module 16 pipeline

All four mechanisms "stop bad things", which is why they get mixed up. A gate judges an output between stages. A hook judges an action inside an agent. A correction loop decides what happens after a FAIL. A checkpoint hands a decision to a person. Bounds and fail-safe defaults sit around all four.

02 — A gate is only as good as its criteria

"Looks good" is not a criterion

Good gate criteria are objective (the same input gives the same verdict), observable (checked from the artifact, not from what the agent claims), actionable (the FAIL message says what to fix), cheap first and versioned in the repo.

gates.yaml: gate G3 (after the Test Generator)

G3_tests_collect_and_conform:
  checks:
    - cmd: pytest --collect-only -q tests/test_req_*.py
    - cmd: ruff check tests/
    - every test has @pytest.mark.ac and .seq
    - changed paths ⊆ ["tests/**", "runs/**"]
  on_fail: retry_producer     # stage 3, with findings
  max_rounds: 2

G4_no_test_defects:
  checks:
    - count(class == TEST_DEFECT) == 0
    - count(class == ENVIRONMENT) == 0
  allow: PRODUCT_DEFECT # flagged, carried on
  max_rounds: 2     # shared counter with G3

Bad → good

  • "tests are reasonable" → pytest --collect-only exits 0
  • "agent says all ACs covered" → every AC-ID appears in ≥ 1 @ac marker
  • "FAIL" → "FAIL: AC-3 has no test; SEQ-3 unmapped"
  • criteria in someone's head → gates.yaml under review

Three outcomes, not two

PASS → next stage.
FAIL → criteria checked and not met; the producer can fix it, so start a correction loop.
NEEDS_HUMAN → can't be decided automatically (ambiguous input, validator error, policy question).

03 — After the FAIL

Send the failure to the stage that owns it, and patch rather than regenerate

Three decisions determine whether a correction loop converges or just churns: who retries (the stage that owns the defect, not simply the last one), what feedback is reused (structured findings plus the previous artifact, not "try again"), and what reruns (only the retried stage and whatever depends on it).

findings.json: structured correction feedback

{
  "gate": "G4_no_test_defects",
  "round": 1, "max_rounds": 2,
  "route_to": "test-generator",
  "artifact_to_modify": "tests/test_req_2481_….py",
  "findings": [{
    "test": "test_cancel_shipped_order_rejected",
    "ac_id": "AC-2",
    "observed": "asserts body['errorCode']",
    "expected": "body['error']['code'] per openapi.yaml",
    "class": "TEST_DEFECT"
  }],
  "do_not_change": ["tests with no findings", "markers"],
  "previous_attempt_summaries": [
    "round 0: fixture make_order missing → fixed"]
}
Why it works

artifact_to_modify makes the agent patch instead of regenerate. do_not_change stops a fix for F-1 from breaking tests that already passed. previous_attempt_summaries stops the agent from trying a fix that already failed. Without these three fields, correction loops tend to cycle between the same few states.

04 — Deterministic code the model can't forget

A rule says what should happen. A hook makes sure it does.

A hook is a script the agent runtime runs automatically at a lifecycle event. It gets JSON describing the event and can allow, deny or ask, and log the result. Use both together: the rule explains why ("never read .env") and the hook enforces it every time.

05 — The most expensive gate, used on purpose

Put a human where an automated mistake would be unacceptable

A human is the slowest, most expensive and most authoritative gate. Add checkpoints where the impact is high or the action can't be undone, not everywhere. Too many checkpoints cause approval fatigue: people start approving without reading, and the checkpoint stops protecting anything.

Checkpoints in the Lab 3 pipeline

  • Ambiguous input: G1 NEEDS_HUMAN → requirement owner answers
  • Before an irreversible action: commit / PR of generated tests
  • After the loop runs out of rounds: round 3 of Generator retries
  • On escalation: Reviewer ESCALATE (DEF-5520)
  • When the control layer fails: validator crashed → human

What the approver sees: a decision packet, not a transcript

## Approval requested: commit tests for REQ-2481
Run:        req-2481-run-03
Decision:   APPROVE / REJECT / REQUEST CHANGES
Gate trail: G1 ✔ G2 ✔ G3 ✔(round 2) G4 ✔ G5 ESCALATE
Coverage:   AC-1..AC-4 → 6 tests · 5 pass · 1 fail
            (DEF-5520, product defect, 404 vs 403)
Diff scope: tests/test_req_2481_….py (+142), runs/…/**
Risk notes: no out-of-scope files; no secrets found
Cost:       61k tokens · 7m 40s · 2 correction rounds
Evidence:   traceability.md · 04_report · gate_log.jsonl
Rule

Record every decision with approver identity, timestamp and reason in the gate log. If an approval wasn't recorded, treat it as if it never happened.

06 — A counter alone is not enough

Stop when the loop stops making progress, not just when it runs out of rounds

Self-correction loops fail in predictable ways. A hard round limit catches runaway loops, but you also need to detect oscillation, stalled progress, and agents that "pass" by weakening the tests.

Runaway

Rounds never end.

Hard max_rounds per gate and per run.

Oscillation

Fix A breaks B, fix B breaks A.

Detect repeated artifact hash or finding set; do_not_change.

No progress

Same findings every round.

Stop if the findings count doesn't drop between rounds.

Goal drift

"Passes" by deleting asserts or adding skip.

Invariants: assertion count ≥ previous; no new skip/xfail without a defect ID.

Budget blow-out

Each round adds context and costs more.

Token/time budget per run; send summaries, not transcripts.

Gate gaming

Agent edits the gate config or test runner.

Hooks deny writes to gates.yaml, pytest.ini, .cursor/**.

07 — Subtopic: decisions on record, safe when things break

If the checker fails, the answer is never PASS

Module 14 logged handoffs. This module also logs decisions: every gate evaluation and every human approval becomes an append-only entry that answers the auditor's question, "why was this allowed through, and by whom or what?" The checkers can fail too. When they do, the pipeline stops rather than continuing.

gate_log.jsonl: one line per evaluation

{"gate":"G3_tests_collect_and_conform",
 "gates_version":"1.0.0", "round":1,
 "input_ref":"tests/…py#sha:c07e",
 "decision":"FAIL",
 "checks":[{"collect":"PASS"},
          {"markers":"FAIL",
           "detail":"test_refund missing @ac"}],
 "routed_to":"test-generator",
 "decided_by":"automated"}

{"gate":"HITL_commit", "decision":"APPROVE",
 "decided_by":"human:qa-lead",
 "reason":"DEF-5520 raised; failing test kept"}

Why each field is there

  • gates_version: a verdict only means something relative to the criteria that produced it
  • input_ref + hash: proves which artifact was judged
  • checks[]: which criterion failed, not just the overall verdict
  • decided_by: automated, llm-judge@v or human:<role>
  • reason: required for human overrides and ESCALATE
What failedFail-open (dangerous)Fail-safe (required)
Gate script crashesMissing verdict treated as PASSNEEDS_HUMAN; halt stage; log the error
LLM judge unparsableAssume approvalRetry once with stricter format, then NEEDS_HUMAN
Sandbox unreachableSkip execution checksENVIRONMENT; retry infra once; then halt
Policy hook errorsAllow the actionDeny (for before* hooks); alert
Log sink downContinue without a trailBuffer locally; block HITL/commit until written
Timeout mid-editKeep partial editsQuarantine; next attempt writes a fresh file

Step 2 · .cursor/hooks/shell-policy.sh

#!/usr/bin/env bash
# stdin: hook event JSON · stdout: allow / deny / ask
# Fail-safe: any unexpected error → deny
set -euo pipefail
trap 'echo "{\"permission\":\"deny\"}"; exit 0' ERR

cmd="$(jq -r '.command // empty')"

case "$cmd" in
  *"git push"*|*"rm -rf"*|*"curl "*|*"wget "*)
    log deny;  echo '{"permission":"deny"}' ;;
  "pytest"*|"ruff"*|"python -m pytest"*)
    log allow; echo '{"permission":"allow"}' ;;
  "pip install"*|"uv add"*)
    log ask;   echo '{"permission":"ask"}' ;;
  *)
    log ask;   echo '{"permission":"ask"}' ;;
    # default: unknown → a human decides
esac

What matters is the shape: an allow-list, an explicit deny-list, ask by default, one log line per decision, and deny on error. Check the current Cursor Hooks docs for exact field names.

09 — Before Day 6

Carry these five ideas forward

01

Gates judge outputs between stages, using objective, cheap-first, versioned criteria with three outcomes: PASS, FAIL and NEEDS_HUMAN.

02

Send each FAIL to the stage that owns the defect, with structured findings. Patch instead of regenerating, and re-run only what depends on the change.

03

Hooks judge actions inside an agent and always run. Rules explain why; hooks make sure it happens.

04

Put humans only where an action has high impact or can't be undone, and show them a decision packet.

05

Limit loops by rounds, progress, budget and invariants. Log every decision, and when a checker fails, the result is NEEDS_HUMAN or deny, never PASS.

What's the difference between a gate and a hook? One example of each from Lab 3.

A gate judges a stage's output between stages, e.g. G3 checks the tests collect and carry AC markers. A hook fires on an action inside an agent's loop, e.g. beforeShellExecution denying git push, or afterFileEdit formatting and logging an edited test.

Why should an LLM-judge verdict never overrule a failing deterministic check?

Deterministic checks are objective and reproducible. An LLM judge is probabilistic and can be persuaded by output that looks plausible. Once code has shown the artifact is broken, a good judged "quality" score doesn't make it usable.

A test asserts a field that isn't in the spec. Who retries, with what feedback, and what reruns?

The Test Generator retries. It gets structured findings (test, AC-ID, criterion, observed vs. expected with a spec citation) and the existing test file to patch. Stages 3 → 4 → 5 rerun, and stages 1–2 are reused.

Why isn't a rule saying "never read .env" enough on its own?

A rule is guidance the model usually follows but can ignore, misread or lose in a long context. A beforeReadFile hook enforces it on every attempt and logs the denial.

The loop has rounds left but produces an identical artifact hash twice. What now?

Escalate now. An identical hash means no progress, so more rounds would just use up budget or oscillate. The progress check overrides the remaining round count.

The gate script crashes. What verdict is recorded, and what must not happen?

NEEDS_HUMAN: halt the stage, quarantine partial artifacts, log the error. It must not be treated as PASS, because continuing without a verdict is failing open.
