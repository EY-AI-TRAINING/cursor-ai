01 — Do's and don'ts; avoiding over-reliance

The agent drafts. You stay the engineer.

Every practice in this programme comes down to one idea: an agent is a fast, tireless, unaccountable contributor. It speeds up drafting, searching and checking. It can't own a decision, and it will state a wrong answer as confidently as a right one. The do's keep you in the loop where it matters. The don'ts are the ways teams quietly drop out of it.

Do

  • Start from a spec with acceptance criteria, not a vague promptModule 9: the spec is the contract the output is judged against.
  • Ground on the right context, not all of itRules, the relevant files, the spec. More context costs more and often answers worse.
  • Plan before you let an agent edit many filesApprove the plan; it's the cheapest checkpoint.
  • Make checks deterministic wherever you canGates, tests, linters and hooks, not "the agent said it's fine".
  • Review diffs like a colleague's PRRead what changed, run it, ask why.
  • Keep humans on intent and risk decisionsPlan approval, sign-off, readiness, anything outward-facing.

Don't

  • Accept code you couldn't explain in reviewIf you can't defend it, you don't own it yet.
  • Let the agent grade its own homeworkUse a separate-context reviewer and real tests.
  • Paste secrets, customer data or production credentials into contextHooks and ignore files stop it; habits matter too.
  • Loop without a budgetCap rounds, tokens and time; escalate instead of retrying forever.
  • Fix a test so it passes a real bugClassify first: test, product or environment.
  • Approve everything, all the timeApproval fatigue turns every checkpoint into a rubber stamp.

Signs of over-reliance, in a person or a team

Skill fade

"Ask the agent"

Nobody can debug the module without an agent open. Keep some tasks hands-on, and rotate who reviews.

Rubber-stamping

Approvals in seconds

Sign-offs arrive faster than anyone could read the diff. Sample and audit them, and reduce how many you ask for.

Plausibility bias

"Looks right"

Output is accepted because it's fluent. Require evidence: a test, a trace, a reference.

Lost context

No why in history

PRs say what changed, not why. Keep the ticket, plan and trailers so decisions stay traceable.

02 — Verifying AI and agent output

Four questions every change must answer, and who checks each

"It compiles and the agent is confident" answers none of them. Verification is layered: cheap deterministic checks run first and catch most problems, then independent review catches what rules can't, and a person decides. Each layer is only worth something if it's independent of the one that produced the change.

Correctness

Does it do what the spec says?

Tests traced to ACs, negative paths, contract checks, run against a real target. Evidence: junit.xml, coverage by AC.

Security

Could it hurt us?

Secret scan, dependency review, SAST, hook logs, least-privilege tools, no untrusted text followed as instructions.

Maintainability

Can we live with it?

Lint, complexity, duplication, naming, matches house patterns (rules), readable by the next person, no dead code.

Traceability

Can we explain it later?

Ticket and AC IDs in markers, trailers and PRs; approvals bound to hashes; evidence linked, not retyped.

03 — Choosing the right Cursor interaction

Match the tool to the task, not the task to the tool

The most autonomous mode is rarely the best. Pick the smallest interaction that does the job: less autonomy means less context, lower cost, faster feedback and an easier review. Move up the ladder only when the task needs more steps, more files or more isolation.

04 — Subtopic · When not to use an agent or autonomous workflow

Sometimes the best agent is no agent

An autonomous workflow pays off when the task is specifiable, checkable and repeatable, and a mistake is cheap to catch. If any of those is missing, the agent adds cost and risk without adding speed. Ask these questions before you reach for autonomy.

The requirement is the question

Pricing rules, legal wording, a product trade-off.

A person decides with the owner. AI can draft options in Ask mode, not choose.

No oracle to check against

No spec, no tests, no reference output.

Write the spec or the test first, then automate.

Irreversible or outward-facing

Production data changes, customer messages, releases.

Human-executed, or agent-prepared with explicit approval and a rollback plan.

Faster by hand

A one-line change you already understand.

Just make it. Setting up context costs more than the edit.

Sensitive context

Regulated data, secrets, production credentials in scope.

Keep it out of agent context entirely, whatever the mode.

Learning is the point

An onboarding task or a new area of the system.

Do it yourself with Ask as a tutor. Understanding is the deliverable.

05 — Rolling out rules, skills, agent patterns and gates across a team

A paved road, not a mandate

What spreads is what's easy to adopt. Package what worked in the capstone as a template: rules, skills, subagent definitions, hooks, gates.yaml, readiness.yaml and the CI workflow, parameterised by one manifest. Then roll it out in phases, each with exit criteria measured, not felt.

shared assets: org level vs. repo level

ai-engineering-assets/    # org repo, versioned
├── rules/                # security, testing, style
├── skills/               # e.g. api-tests
├── agents/               # reviewer, generator
├── hooks/                # mcp-policy, guards
├── policies/gates.yaml   # tighten, never loosen
├── policies/readiness.yaml
├── templates/capstone.yaml # paved road
├── evals/                # regression set
└── CHANGELOG.md

service-repo/.cursor/     # pins assets@v2.3.1
Tighten, not loosen

Repos inherit the org baseline and may add stricter rules or gates. Loosening one (for example removing the secret-deny hook) requires the asset owner's review. That's what makes central governance and local ownership compatible.

Enable, then measure

Each phase needs champions, office hours and a feedback channel. Track adoption (active users, runs per week) alongside outcomes (rounds per run, escaped defects), not instead of them.

Admin controls

Use organisation-level settings for privacy mode, allowed models, MCP servers and background agents rather than asking each engineer to configure them. Check your Cursor plan's admin features.

06 — Token economics

An agent re-reads its context on every call

The price of one call is easy: tokens in × input rate + tokens out × output rate. The price of a task is what surprises people. An agent loop makes dozens of calls, and each one re-sends the grounding context plus the growing history. Grounding size multiplies across every call, so targeted context is a cost control, not only a quality one.

the model

cost_per_call =
    ctx_tokens × (1 − cache_hit) × in_rate
  + ctx_tokens × cache_hit       × cached_rate
  + out_tokens                   × out_rate

cost_per_task  = cost_per_call × calls_per_task
cost_per_month = cost_per_task × tasks_per_month

07 — Building an ROI case

Time saved vs. token spend vs. defect reduction

A credible ROI case counts all the costs, including review time, enablement and keeping the assets maintained, and measures benefits against a baseline taken before rollout. Capstone-style run logs give you the cost side almost for free. Time saved and defects avoided have to be measured, not assumed.

Measure these

Common inflation

Counting "hours saved" from self-reports, ignoring review and rework time, or crediting the AI with defect reductions that came from adding tests. An honest, smaller number survives a finance review; an inflated one doesn't.

08 — Defect logs and production feedback → grounding

Every escaped defect is a missing rule, example or test

Grounding sources (rules, skills, specs, examples, test patterns, reviewer checklists) go stale as the system changes. The best signal for what's missing is what got through. Route defects and incidents back into the assets that should have caught them, and test the change before you release it, like any other code.

Keep a regression set

Store past tickets, runs and known-bad outputs under evals/. Every change to a rule, skill or prompt must still catch the defects it caught before. Without that, an "improvement" can quietly undo an earlier fix.

09 — Ownership, governance, versioning, review and maintenance

Shared AI assets are production code. Treat them that way.

A rule file changes the behaviour of every agent run in every repo that uses it. That makes it as consequential as a shared library, so it needs what a shared library has: a named owner, semantic versions, review before release, a changelog, tests, and a date by which someone checks it's still true.

Version in every log

Every run records which asset versions it used (gates_version, rule and prompt hashes). When behaviour changes, you can tell whether the model changed, the asset changed, or the input did.

Expiry dates

Give every asset a review_by date. An asset nobody has reviewed in six months is a guess about how the system used to work.

10 — Subtopic · Maintenance, monitoring and continuous improvement

Lifecycle phases, not a one-time handoff

The pipeline you built is a living system: models change, the codebase changes, tickets change. Without monitoring it degrades silently. Gates still pass while the tests get shallower, and costs creep up one round at a time. Watch a few signals, give each one an owner, and decide in advance what action it triggers.

First-try gate pass rate

71%

Falling: a grounding source is stale. Check recent escapes and rule changes.

Rounds per run

1.4

Rising: generator rules or skills need examples; look at the top finding type.

Escalation rate

9%

Rising: tickets are less specifiable, or the gates are too strict. Sample the escalations.

Cost per ticket

2.9

Creeping: context growth or a model change. Compare per-stage tokens in run_log.

Human–AI review disagreement

18%

Rising: the reviewer contract has drifted. Update examples; re-run the regression set.

Escaped defects / release

0.6

Falling: keep it that way. Every escape still enters the feedback loop.

Cadence

Weekly: glance at the dashboard, triage escalations. Monthly: review the defect → grounding backlog, release asset updates. Quarterly: re-baseline ROI, review access and MCP scopes, retire unused skills, re-check models and pricing.

11 — Subtopic · Common pitfalls in orchestration

How multi-agent workflows go wrong, and how to avoid it

Unbounded loops

Retries until the tests pass or the budget is gone.

Shared round cap, no-progress detection, escalate to a human (Module 18).

Shared-context reviewers

The reviewer agrees with everything the generator did.

Separate context, files only, its own contract and checklist.

Soft gates

"Please make sure tests have markers" in a prompt.

Deterministic checks in code; prompts guide, gates decide.

Over-orchestration

Seven agents for a job one prompt and a test would do.

Start with one agent plus gates; split only where isolation or parallelism pays.

Hidden state

Agents pass results in chat, so nothing can be replayed.

Artifacts on disk with hashes; every stage reads files and writes files.

Approval everywhere

Humans asked at every stage start clicking through.

Two meaningful checkpoints, bound to hashes; automate the rest.

Trusting inputs

A ticket comment changes what the agent does.

Untrusted text quarantined as data; write tools behind "ask".

Fail-open hooks

The policy script crashes and the action goes through.

Deny on error, and test that path.

No cost visibility

The bill arrives before anyone knew a run took 1M tokens.

Per-stage token logging, budgets per run, alerts on outliers.

13 — Programme recap

One workflow, from requirement to deployment readiness

Programme outcome: a practical Cursor-based AI-assisted engineering workflow spanning requirements, planning, specification, implementation, testing, review, governance, CI/CD and deployment readiness. It rests on five layers of engineering discipline, each building on the one below.

  1. Prompt engineeringClear task instructionsM1–M5
  2. Context engineeringThe right repository, specification, standards and knowledgeM4, M9, M12, M13
  3. Agent engineeringRoles, tools, guardrails, skills and subagentsM8, M10–M16
  4. Workflow engineeringStages, gates, correction loops, hooks and approvalsM17–M19
  5. AI-assisted SDLCAll of the above, applied systematically from requirement to readinessM20–M21
01

Use the smallest interaction that does the job, and know when the answer is no agent at all.

02

Verify in layers: deterministic checks, independent review, then a human decision on intent and risk.

03

Cost per task is dominated by context × calls. Targeted grounding and fewer rounds are the biggest levers.

04

ROI counts review, enablement and upkeep, and is measured against a baseline, not assumed.

05

Shared AI assets are production code: owned, versioned, reviewed, tested and maintained, with defects and incidents feeding back into them.

Your agent's output compiles and the tests it wrote pass. What's still unverified?

Whether the tests match the spec (they could assert the bug), security (secrets, dependencies, unsafe calls), maintainability against house patterns, and traceability to the ticket and ACs. Independent tests, gates and a separate-context review cover those; a human decides.

Why can doubling the grounding context more than double the cost of a task?

Context is re-sent on every call in the loop, and larger contexts tend to lead to more calls and rounds when relevant signal is diluted. Caching helps with repeated prefixes, but growing history is not cached. Narrow grounding and isolated subagent contexts keep both factors down.

A sponsor says "the AI saves two hours per ticket". What do you ask?

Measured how and against what baseline? Is review and rework time included? What are token, seat and upkeep costs? Did defect rates change, and is that change attributable to the workflow or to the extra tests? A defensible case survives those questions.

A production incident reveals a pattern your reviewer agent never flags. What's the full fix?

Classify the root cause, update the reviewer checklist or rule with an example, add the case to the regression set, check the updated asset catches it without losing earlier catches, bump the version, release through review, and watch the disagreement and escape metrics.

Who should own the organisation's shared reviewer-agent definition, and why not "everyone"?

A named quality owner, with CODEOWNERS on the file. "Everyone" means nobody reviews changes, nobody maintains the regression set, and behaviour drifts without anyone noticing.

Name two situations where you'd deliberately not use an autonomous workflow.

For example: when the requirement itself is the open question (a business decision), when there's no oracle to check against, when the action is irreversible or outward-facing, when sensitive data would enter the context, or when learning the area is the point.

After the programme

Next 30 days: apply the workflow to one real ticket type in your team, with the capstone template and a baseline. 60 days: publish your rules, skills and gates as versioned shared assets with named owners. 90 days: report cost per ticket, rounds, escaped defects and time saved against the baseline, and decide what to scale.
