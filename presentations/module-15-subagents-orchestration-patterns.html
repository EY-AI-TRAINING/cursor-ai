01 — Two basic shapes

Sequential when each step needs the last one's output. Parallel when it doesn't.

A sequential chain is easy to reason about: one input, one output, one place to look when it breaks. Fan-out/fan-in cuts wall-clock time, but only when the branches really are independent, and you then need a merge step to reconcile what comes back.

02 — What actually crosses the arrow

A handoff is a contract, not a chat transcript

The next agent should not have to read the previous agent's whole conversation. It gets a small, typed payload plus pointers to artifacts on disk. The pipeline's state (which step, which attempt, what passed) sits with the orchestrator, not inside any single agent's memory.

Put in the handoff

  • Status and a one-line reason
  • Paths to produced artifacts
  • Assumptions made and open questions
  • Run / trace id so the next step can log under it

Keep out of the handoff

  • The previous agent's full reasoning or chat log
  • Whole files pasted inline
  • Secrets or credentials (Module 14)
  • Instructions that override the next agent's role

03 — One job per agent

Four roles, each with a clear input, output and boundary

A role is worth having if it asks a question no other role asks. These four are the backbone of Module 16's lab. Note what each one is not allowed to do: that restriction is what keeps them independent.

Step 1

Validator

"Is this input complete and testable?"

In
Raw requirement
Out
PASS/FAIL + gaps list
Must not
Invent missing details

Step 2

Builder

"What's the structure or sequence?"

In
Validated requirement
Out
Ordered test sequence / plan
Must not
Write executable code

Step 3

Generator

"Turn the plan into working artifacts."

In
Sequence + repo conventions
Out
Code / tests (e.g. PyTest)
Must not
Change the plan silently

Step 4

Reviewer

"Does the output match the source?"

In
Artifacts + original requirement
Out
Sign-off or change requests
Must not
Fix what it reviews

04 — Fresh context on purpose

Subagents start clean and return only a summary

When the parent agent delegates, the subagent gets a brief, not the parent's history. It can read 40 files, run searches and try things, and all of that noise stays in its context. The parent gets back a short result and keeps its own context for coordinating.

Delegate when…

  • The subtask is noisy (search, exploration, long logs)
  • You need an unbiased second opinion
  • Branches can run in parallel
  • The subtask needs different tools or tighter permissions

A good brief contains…

  • Goal plus a definition of done
  • Exact inputs (paths, ids), not "see above"
  • Constraints: read-only? which folders?
  • The shape of the answer you want back

05 — Every loop needs an exit

Retry with feedback, time out, then stop and escalate

Agents fail in quieter ways than code does: wrong output that looks right, loops that never converge, tool calls that hang. Every step needs three limits (attempts, time, budget) and a defined thing that happens when a limit is hit. Silently continuing should never be that thing.

max_attempts 3 step_timeout 120s max_turns 25 run_token_budget 200K on_exhaust stop + escalate retry_scope this step only

06 — The cheapest agent is the one you didn't add

Climb the ladder only as far as the problem needs

Each extra agent adds a handoff, a failure point, latency and cost (Module 14's cost table). Start at the lowest rung that works. Only move up when you can say which specific problem the next rung solves.

Split into another agent only if one of these is true

  • It needs a different context (would pollute or bias the current one)
  • It needs independent verification
  • It needs different tools or permissions
  • It can run in parallel and time matters

Smells of over-orchestration

  • An agent whose output is just passed straight through
  • Two agents that always need each other's full context
  • "Manager" agents managing one worker
  • More handoff code than task logic

07 — Subtopic: seeing across handoffs

One run id, one span per agent, one line per handoff

Module 14 introduced tracing and handoff logs. In a pipeline they answer the first debugging question: which handoff went wrong? A failure at the Reviewer is usually caused two steps earlier, and the trace is what lets you follow it back.

08 — Subtopic: where Cursor ends and your pipeline begins

Cursor-native orchestration vs. external workflow orchestration

Inside Cursor, the agent is the orchestrator. It decides when to delegate, in an interactive session with a developer watching. An external orchestrator (CI job, script, workflow engine) owns the control flow in code and calls agents as steps. Most teams need both, and they should know which layer owns which guarantee.

ConcernCursor-nativeExternal orchestration
Who decides next stepThe agent, guided by rules / skills / promptsCode: explicit DAG or state machine
StateSession context + files in the workspaceDurable store that survives restarts
Retries & timeoutsWithin the session; bounded by prompt and hooksEnforced by the runner, per step, across runs
Human roleWatching and steering liveExplicit approval checkpoints
Best fitInteractive build, explore, refactor, reviewRepeatable, scheduled or unattended pipelines

09 — Hands-on: read a pipeline diagram like a reviewer

Walk the sample pipeline, one numbered point at a time

This is the Module 16 pipeline drawn with everything from this module on it. Go through the numbered points as a group. For each one, ask: what's the contract, what's the bound, and what gets logged?

  1. Entry gateThe Validator rejects early. An incomplete requirement goes back to its author, not further down the chain.
  2. Handoff contractWhat fields cross this arrow? Which are passed by path rather than inline?
  3. Sequential or parallel?Could API validation run beside generation, or does it need the generated tests first?
  4. Retry loopWho retries (the Generator), what feedback is reused, and what is the cap?
  5. Independent reviewerWhy is it a subagent with its own context? What does it read directly?
  6. Fail-safe pathWhat state is kept when a limit is hit, and who receives the escalation?
  7. Trace & orchestratorNative Cursor session or external runner? What does one run's trace show end to end?
  8. Your turnRedraw it with one agent removed. What would you lose, and would anyone notice?

10 — Before the lab

Carry these five ideas into Module 16

01

Go sequential when steps depend on each other and parallel only when branches are truly independent. Pass state through small, typed handoffs.

02

Each role asks one question and has one thing it must not do. Validator, Builder, Generator and Reviewer stay separate for that reason.

03

Subagents give you a clean context: less noise for the parent, and a reviewer that hasn't already been persuaded.

04

Every step gets attempt, time and budget limits, retries carry the failure reason, and hitting a limit means stopping and escalating.

05

Add agents only for a named reason, trace every handoff under one run id, and decide which guarantees come from Cursor and which from an external orchestrator.
