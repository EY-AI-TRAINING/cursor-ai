01 — The mission

The components are built. Today proves they compose.

Lab objective: transform a Jira or Azure DevOps ticket into a requirement bundle, an approved plan and spec, a test sequence, executable tests, validation evidence, an independent review, a deployment-readiness check, and a traceable final engineering report. Deliverable: a complete report package, ready for stakeholder sign-off, including an observability and cost summary.

Reused as is

The control plane

Rules, hooks, gates.yaml, readiness.yaml, mcp.json and the CI workflow from Modules 17–19.

New today

An unseen ticket

The facilitator hands out a sandbox ticket on the day. Its ACs may be prose, ambiguous or incomplete.

New today

Plan approval

A recorded human approval of the implementation plan before any code or tests are generated.

New today

The report

One document that ties every artifact together for a stakeholder, with cost and a decision request.

Activities, in order

  1. Pull a sandbox ticketVia MCP (or the mock server), and extract a schema-valid requirement bundle.
  2. Explore and planRead the repository, draft an implementation plan, and obtain a recorded human approval.
  3. Spec noteA short spec that fixes the acceptance criteria, one to one with the bundle's AC-IDs (Module 9 SDD).
  4. Test sequenceGenerate the engineering test sequence from the requirement bundle (Module 16).
  5. PyTest + executionGenerate the suite, run it against the sandbox target, classify every failure.
  6. Validation → reviewProduce a validation report and route it to an independent reviewer agent in a separate context.
  7. GatesRun the security/quality and deployment-readiness gates from Modules 17–19.
  8. Delegate (optional)Demonstrate background execution of one isolated task, with its delegation checklist.
  9. ReportCompile the checklist and the final report: ticket → plan → spec → sequence → tests → results → review → readiness.

02 — Capstone architecture

Four layers: people decide, agents do, evidence accumulates, policy governs

Nine agent stages do the work. People appear only where the decision is about intent or risk: agreeing the ACs, approving the plan, signing off the tests, deciding readiness, and signing off the report. Every stage writes to one run folder, and the report is compiled from that folder rather than written from memory. The control plane underneath is owned by people through CODEOWNERS; agents read it and never edit it.

Two checkpoints, not ten

CA-2 (plan approval) and CA-7 (hash-bound sign-off) are the two approvals the capstone requires. AC confirmation and the readiness call are decisions people already own. Adding an approval at every stage produces approval fatigue, and the rubric marks it down.

One key

The ticket ID and AC-IDs travel through every layer: bundle, plan header, spec, scenario IDs, test markers, commit trailers, PR title, readiness report and final report. If grep REQ-2517 misses a layer, traceability is broken there.

03 — Roles and a suggested day plan

Everyone leads something; nobody signs off their own work

Teams of 3–4, five roles, one person may hold two. The only hard rule: the quality lead who signs off the tests is not the person who generated them. Otherwise the sign-off is a formality, not a control. The time boxes below are a suggestion; your facilitator sets the real schedule.

05 — Ticket → bundle → approved plan · CA-1, CA-2

The cheapest checkpoint in the whole run is the plan

Pull the ticket read-only through MCP, exactly as in Module 19: the hook allows get_ticket, the bundle is schema-valid, ticket text stays data, and a ticket that isn't Ready for Dev stops the run. Then the agent explores the repository and drafts a plan. A wrong plan caught here costs minutes; the same mistake caught at review costs the whole run.

plans/REQ-2517/plan.md (excerpt)

# Plan — REQ-2517 · change delivery address
Ticket: REQ-2517 · rev 3 · bundle 00@91d2

## What I found in the repo
- PATCH /orders/{id}/address in openapi.yaml v2.4
- order states: PLACED → PICKING → DISPATCHED
  → DELIVERED (src/orders/state.py)
- tests/api/ has fixtures for owner + other user

## Approach
1. Spec note: AC-1…AC-4, one to one with bundle
2. Sequence: happy paths + each rejection state
3. Tests: tests/api/test_req_2517_address.py
4. Run vs SANDBOX_URL; classify every failure

## Out of scope
- Changing the endpoint itself (tests only)
- Address validation rules beyond postcode

## Risks / questions
- AC-3 error body shape: contract says
  errors[].field — confirm the owner agrees

Recorded, bound, before

The approval names the plan's hash, so editing the plan afterwards invalidates it. A hook or next_step.py refuses to start spec or test generation until approval.json exists and matches plan.md. That's what makes CA-2 checkable instead of claimed.

Stop conditions

Ticket not Ready for Dev (like REQ-2490), required fields missing, or ACs that can't be tested: stop, write the reason, and ask the ticket owner. Don't guess the requirement.

06 — Spec note, sequence, tests, execution · CA-3, CA-4, CA-5

Every test points at an AC. Every failure gets a class.

The spec note is short on purpose: it fixes the ACs, with IDs that match the bundle one to one, plus the examples that make each one testable. The sequence and the suite are generated from the spec, and every test carries req and ac markers so coverage is computed, not asserted.

specs/REQ-2517-spec-note.md (excerpt)

# Spec note — REQ-2517
Ticket: REQ-2517 · rev 3 · plan 4b9c (approved)

| AC   | Given / when / then                     |
|------|-----------------------------------------|
| AC-1 | order PLACED or PICKING → PATCH address |
|      | → 200, response has the new address     |
| AC-2 | order DISPATCHED or DELIVERED → 409,    |
|      | stored address unchanged                |
| AC-3 | invalid postcode → 422,                 |
|      | errors[].field == "postcode"            |
| AC-4 | caller is not the order owner → 403,    |
|      | stored address unchanged                |

Out of scope: the endpoint's implementation.

@pytest.mark.ac("AC-2")
@pytest.mark.parametrize("state",
    ["DISPATCHED", "DELIVERED"])

        api, order_in, state):

Classify every failure before anything reacts to it

Test defect

The test is wrong

Wrong expectation, missing marker, brittle fixture. Goes back to the generator as a correction round.

Product defect

The product is wrong

The test matches the spec and the failure reproduces. Raise a DEF, mark xfail(strict=True), and never "fix" the test to pass.

Environment

The sandbox is wrong

Timeouts, 5xx from a dependency, expired token. Retry once, record it, and escalate. It doesn't use up a correction round.

07 — Validation, independent review, gates, readiness · CA-6, CA-7, CA-8

The reviewer never sees how the tests were made

The validation report goes to a reviewer agent running in a separate context: it reads files, not the generator's chat, reasoning or drafts. Gates catch what can be checked mechanically. The reviewer catches what can't, such as a test that passes without checking what the AC says. Then CI replays the gates on a clean runner and the readiness policy decides.

CA-7 needs a real round

The package must show at least one self-correction round in the gate log. If your run happens to pass first time, seed a realistic fault (remove one @ac marker), record that you seeded it, and show the round. Don't fake a log line.

READY ≠ deployed

The readiness verdict makes the change eligible. A person still approves the environment deployment, and the report still needs stakeholder sign-off.

08 — Optional: delegated / background execution · CA-10

Delegate one isolated task, and prove it was safe to

CA-10 is optional and scored under security and governance. Pick a task whose output is a commit on a branch you review, with nothing to decide on the way. Keep anything that is a judgement, an approval, or a change to the control plane local and human.

Good candidates

Re-run the full suite against the sandbox from a clean VM and attach junit.xml to the PR · apply one reviewer comment on the PR branch · regenerate the traceability table from Git trailers.

Keep local

Plan approval, test sign-off, the readiness decision, defect classification disputes, and any edit to .cursor/, .github/, gates.yaml or readiness.yaml.

Delegation checklist: fill in all five, name the gaps honestly

Environment

Pinned and isolated

Environment config in the repo, pinned hashed deps, fixed install step.

Secrets

Sandbox only

Short-lived SANDBOX_TOKEN, never production, never echoed into files.

Network

Allow-listed

Sandbox API, package mirror, GitHub. Nothing else.

Permissions

Branch, not main

Repo-scoped app; push to agent/* only; can't edit workflows.

Human review

PR, never merge

Required code-owner review; the delegated commit is reviewed like any other.

09 — The final engineering report · CA-9

Any AC, ticket to readiness, in under a minute

That's the rubric's bar for "excellent" traceability. The report is written for a stakeholder who wasn't in the room: it opens with the decision you are asking for, and every claim links to an artifact. Most of it is generated from the run folder, Git trailers and CI; people write the summary, the risks and the recommendation.

Trace an acceptance criterion through the package

Pick an AC. Each hop shows what the package says and where the evidence lives.

    Generated, not retyped

    The traceability matrix, result counts, gate trail and cost table come from junit.xml, gate_log.jsonl, run_log.jsonl and git log --format='%(trailers)'. A number typed by hand will eventually disagree with the evidence, and a reviewer will find it.

    The stakeholder test

    Hand the report to someone outside the team. If they have to ask a question before they can decide, the answer belongs in section 1.

    10 — Observability and cost

    Tokens, time, rounds and escalations, per stage

    Every stage appends one line to run_log.jsonl. The report's cost section is a table built from that file, plus one improvement idea that the numbers justify. Illustrative numbers for run 01 below; model pricing varies, so report tokens and time, and convert to money with your organisation's rates.

    One improvement

    The test generator used about a quarter of all tokens over three generations. Round 1 was a missing AC. Adding "every bundle AC has ≥1 test" to the generator's own rule would likely have saved that round, roughly 20k tokens and 4 minutes per run.

    Count human time too

    The two approvals waited 12 and 9 minutes. For the stakeholder, wait time is part of the cost of this workflow.

    13 — Pitfalls under deadline

    What goes wrong on capstone day, and the fix

    Approved after the fact

    Tests were generated, then the plan was written and "approved" to match.

    Enforce the order: generation refuses to start without an approval.json whose hash matches plan.md.

    AC drift

    The spec renumbers or merges ACs, and the bundle's AC-3 is now the spec's AC-2.

    G1 checks set equality by ID. Clarifications change the bundle through the owner, never silently in the spec.

    Status-code-only tests

    Every test asserts 409 and nothing else, so "address unchanged" is never checked.

    The reviewer checks each assertion against the AC text. Gates can't catch this; separate-context review can.

    Everything is a product defect

    Failing tests get marked xfail to turn CI green.

    A product defect needs a spec-matching test, a reproduction, and a DEF ID. The quality lead signs the classification.

    Hand-typed report

    The report says 6 passed; junit.xml says 5 passed, 1 xfailed.

    Generate the tables from the evidence files, and write only the summary, risks and recommendation by hand.

    Roles decided at 3 pm

    The author signs off their own tests because nobody else is free.

    Bring the Lab 19.8 charter. Roles, sign-off owners and the top three risks are settled before the ticket arrives.

    14 — Before Day 8

    Carry these five ideas forward

    01

    The capstone adds little new machinery. It proves the pieces compose on an unseen ticket, under deadline, with real roles.

    02

    Two human checkpoints: plan approval before generation, and a hash-bound sign-off on the tests. Both are recorded and checkable.

    03

    Every failure is classified as test, product or environment before anything reacts. Product defects become strict xfails with a DEF ID, never a rewritten test.

    04

    Review in a separate context catches what gates can't. CI replays the gates, and readiness is a versioned policy, not a feeling.

    05

    The report is compiled from evidence: any AC can be traced from ticket to readiness in under a minute, with cost per stage and one improvement the numbers justify.

    Why does the plan approval have to come before any code or tests are generated?

    It's the cheapest point to catch a wrong direction: a bad plan caught there costs minutes, while the same error caught at review costs the whole run. Binding it to the plan's hash, and making generation refuse to start without it, turns "we approved it" into something a reviewer can check.

    A test fails. What do you establish before anyone changes anything?

    Its class. Does the test match the spec? If not, it's a test defect and goes back to the generator as a round. If it does and the failure reproduces outside the test, it's a product defect: raise a DEF, mark it strict xfail, and let a human own severity. If it doesn't reproduce, treat it as environment: retry once, record, escalate.

    Your run passed every gate first time. How do you meet CA-7?

    Seed a realistic fault (for example, remove one @ac marker), record in the report that it was seeded, and show the gate catching it and the bounded round fixing it. Never edit a log to show a round that didn't happen.

    Why does the reviewer agent run in a separate context from the generator?

    If it shares the generator's reasoning, it inherits the generator's blind spots and tends to agree with it. Reading only the spec, sequence, tests and results, it judges the tests the way a stranger would, which is what independent review means.

    Readiness says READY. Is the change deployed?

    No. READY makes it eligible. A person approves the environment deployment, and the stakeholder signs off the report. Agent PRs never auto-merge.

    What makes a cost summary useful rather than decorative?

    Per-stage tokens, time, rounds and escalations from run_log.jsonl, human wait time included, and one concrete improvement that the numbers justify, with its expected saving.
