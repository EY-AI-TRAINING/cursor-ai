01 — Design it, don't dump it

Context is designed, not dumped

More context isn't better context. Everything technically available to an agent — the whole repo, every doc, full history — gets filtered down to what this specific task needs: selected for relevance, structured so the agent can use it, and scoped tightly enough to stay inside the context window.

02 — Five kinds of ground truth

Grounding sources are not interchangeable

Repo code, SRS/SDS documents, standards, historical defects, and enterprise knowledge each answer a different question. An agent citing "the spec" when it actually read a stale doc is still hallucinating — it just has a source attached now.

03 — The protocol, not the magic

MCP is a standard way to plug in the outside world

Model Context Protocol gives Cursor one common interface to external systems: resources it can read and tools it can invoke, both exposed by an MCP server that sits in front of whatever actually holds the data — a ticket tracker, a document store, a database, an internal API.

04 — Different questions, different lookups

Match the retrieval strategy to the question

Semantic search finds what's similar in meaning, a structured lookup finds what's known by exact key, and graph traversal follows relationships between artifacts. Using the wrong one doesn't just retrieve less — it can retrieve confidently wrong context.

05 — Confident is not the same as correct

Hallucination risk scales with how sure the answer sounds

An engineering agent that states an API contract, a compliance rule, or a defect history from memory instead of a retrieved source is dangerous precisely because it sounds no less confident when it's wrong.

06 — Subtopic: no unsupported facts

Every claim needs a source, or it needs to say "unknown"

The guardrail is simple to state and easy to skip under pressure: an agent may only assert what it can point to. If nothing in the retrieved context supports a claim, the answer is "not found in the provided sources" — never a best guess dressed up as fact.

07 — Subtopic: retrieval is not action

Reading a source and acting on it are two different steps

Retrieval — searching docs, fetching a resource, reading repo code — should never carry side effects. Only after grounded context is assembled does an agent cross into the action lane: running tests, modifying files, calling a tool that changes something.

08 — Subtopic: three ways to supply context

Repo context, rules/skills, or MCP — pick by task shape

A one-off question about this codebase usually just needs direct repo context. A pattern the team repeats belongs in a rule or skill. A live external system needs MCP. Reaching for MCP when a rule would do just adds a server to maintain for no benefit.
