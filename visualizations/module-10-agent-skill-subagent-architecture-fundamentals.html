05 / Repository-level rules vs. team-level skills libraries

Two different radii of reuse

A rule travels with one repo. A skill library travels with the team, across every repo they touch.

📁 Repository-level rules

.cursor/rules/*.mdc in this repo only

Scoped to one codebase. Applies automatically via globs. Perfect for "this is how this project does it" — conventions that don't necessarily hold anywhere else.

👥 Team-level skills libraries

shared-skills/ — versioned, imported into every repo the team owns

Scoped to the team, not one repo. Invoked by name wherever it's needed. Perfect for "this is how we generate a changelog" — capability that should be identical everywhere.

Rule of thumb: if the instruction only makes sense inside this one repo, it's a rule. If it should behave identically in every repo your team owns, it belongs in the shared skills library.

07 / Subtopic: versioning and reviewing agent/skill definitions like code; avoiding unnecessary agent decomposition

Reviewed like code. Sized like code.

An agent definition changes the same way a source file does — through a diff, reviewed before merge.

Committed and reviewed like any other change:
# agents/test-generator.agent.yml
- tools: [read_file, write_file]
+ tools: [read_file, write_file, run_tests]
+ guardrails:
+ - Stop and ask if coverage target cannot be met

📌 Recap

Day 3 continues: the vocabulary for everything that follows

  • Rule, prompt, skill, agent, and subagent each have a distinct scope and trigger — they are not interchangeable words for "AI instruction."
  • A reusable agent definition has five parts: role, inputs, tools, guardrails, and outputs — guardrails are what it must never do, not what it can do.
  • Subagent delegation hands off focused work with isolated context, so only a structured result returns to the main agent — not its scratch work.
  • Parameterized prompt templates use placeholders so the same reusable prompt produces a consistent result for anyone who fills it in.
  • Repository-level rules scope to one repo; team-level skills libraries scope to the whole team, across every repo they own.
  • Reusable workflows chain Cursor-native capabilities — agent mode, subagents, skills — with rules enforcing standards silently throughout.
  • Agent and skill definitions are versioned and reviewed like code, and a new subagent should only exist for genuinely independent, isolable work — not by default.
