01 / How LLMs generate text

One token at a time, and nothing more mysterious

An LLM doesn't "know" the ending of a sentence when it starts. At each step it looks at everything so far and produces a probability for every possible next token — then one gets picked, gets appended, and the whole thing repeats. This is autoregressive generation. Try it below: click a candidate at each step (the boldest bar is what the model would pick by default).

This is a simplified, hand-scripted illustration — real models choose from a vocabulary of tens of thousands of tokens at every single step, using probabilities learned from massive training data, not a fixed script like this demo.
02 / Tokens & context windows

Models don't read words. They read tokens.

A token is roughly a word-piece — short words are usually one token, longer or unusual ones get split into chunks. Everything the model can "see" at once — your instructions, the files you attached, the whole conversation — has to fit inside a fixed budget called the context window. That budget is exactly why agent and tool design has to be deliberate about what gets included.

03 / Prompting fundamentals

Same model, wildly different results

Three levers do most of the work: how clear your instruction is, whether the model has examples to pattern-match against, and the split between system prompts (persistent rules) and user prompts (per-turn asks).

Instruction clarity

Vague
"fix the bug"
Here's a general approach: add error handling, double-check your inputs, and review recent changes for anything that looks off.
clarity score: 18%
Clear
"Fix the NullPointerException in UserService.getProfile() (line 42) — it happens when user.email is null. Add a null check and return HTTP 400 'Email required' instead of crashing. Keep the method signature unchanged."
Added a null check before line 42: if user.email is null, return 400 with "Email required". Signature unchanged, 1 file touched.
clarity score: 94%

04 / Capabilities & known limitations

Fluent is not the same as correct

Generative AI is remarkably capable — and has specific, predictable failure modes. Knowing the shape of these limitations is what makes the rest of this course (verification, grounding, agents with guardrails) make sense.

Developer
What's the syntax to retry a fetch using requests.retry_with_backoff()?
Model
You can use requests.retry_with_backoff(url, max_attempts=3, backoff_factor=2) — it automatically retries failed requests with exponential backoff.
Fabricated. requests.retry_with_backoff() does not exist in the requests library. The real approach uses urllib3.util.Retry wired into an HTTPAdapter. The answer was fluent, confident, specific — and wrong. That combination is exactly what makes hallucination dangerous.

Every model has a training data cutoff. Anything that happened after that date is a blind spot unless the model is explicitly grounded with fresh information (search, docs, your repo).

Training data beginsTraining cutoffToday
Example: ask about a library version released after cutoff, and the model may not know it exists — or may confidently describe an older version as if it were current.

Same prompt, run more than once, can produce different — often equally valid — outputs. This is the opposite of how traditional code behaves.

05 / GenAI vs. traditional software

Same input. Different guarantee.

This is the core mental shift for engineers: traditional code is a fixed set of rules — same input always yields the same output. A generative model is probabilistic — same input can yield different, plausible outputs. Press "Run" on each panel a few times.

"How do we currently handle retry logic for the payment API?"
Raw LLM — no grounding
A common approach is to wrap your HTTP call in a retry loop with exponential backoff — e.g. retry up to 3–5 times, doubling the delay each attempt, and give up after a max threshold. Libraries like tenacity or retry can help implement this pattern.

📌 Recap

What to carry into Module 2

  • LLMs generate text one token at a time, guided by learned probabilities — not lookup or search.
  • Tokens and context windows are hard constraints that shape everything about agent and tool design.
  • Clear instructions, well-placed examples, and system/user prompt separation change output quality dramatically.
  • Hallucination, knowledge cutoffs, and non-determinism are predictable, not occasional — design around them.
  • GenAI is probabilistic where traditional software is deterministic — that gap is why verification matters.
  • The SDLC ladder — prompt-driven → context engineering → agents → multi-agent — is the spine of this entire course.
  • Grounded, codebase-aware answers beat generic ones. That's the whole reason Cursor exists.
