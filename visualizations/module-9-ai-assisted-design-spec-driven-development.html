Spec versioning & change management

A security review changed REQ-3.2 after v1.0 shipped. The spec is versioned like code — and code/tests must catch up to match.

# spec/password-reset.md — v1.0 → v1.1
- REQ-3.2: Reset link expires after 60 minutes.
+ REQ-3.2: Reset link expires after 15 minutes and is single-use.
# changelog: v1.1 — tightened expiry + added single-use per security review, 2026-02-11
# downstream: resetPassword.ts, resetPassword.test.ts flagged as out-of-sync until updated

06 / Architecture Decision Records (ADRs); translating SRS → SDS with AI assistance

Recording why, not just what

A spec says what to build. An ADR records why one option was chosen over the alternatives — so nobody re-litigates it in six months.

SRS → SDS, with AI assistance

Cursor helps translate a business-level requirement into a technical design — a human still owns the decision.

📄 SRS (business requirement)

"Users must be able to securely reset a forgotten password without contacting support."

What the business needs — no implementation detail.

⚙️ SDS (technical design, AI-drafted)

"POST /auth/reset-request issues a hashed, single-use token (15 min TTL) via the existing email service; see ADR-002 for token storage."

Specific enough for an agent to implement, and a reviewer to approve.

07 / Subtopic: what belongs in a spec vs. a prompt; acceptance criteria as testable spec clauses; human approval before implementation

Sort it: spec, or just the prompt?

Some things belong in the durable spec. Some are fine as throwaway context in the prompt that asks the agent to implement it. Select the items that belong in the spec.

✅ Acceptance criteria as testable spec clauses
Given a token older than 15 minutes
When the user submits it to /auth/reset
Then the API returns 410 Gone and no password changes

Given/When/Then converts straight into a test — that's what "testable" means here.

🚦 Human approval before implementation
Draft spec→ Team review→ 🚦 Approval gate→ Agent implements

Nothing crosses the gate on a hunch — the agent implements against an approved spec, not a draft.

📌 Recap

Day 3 begins: design and spec, locked in

  • Spec-Driven Development treats a structured, versioned spec as the durable source of truth an agent implements against — unlike prompt-driven or vibe-coding, which leave no lasting artifact.
  • A spec has a fixed shape: overview, requirements, acceptance criteria, interfaces, and out-of-scope — not a wall of unstructured prose.
  • Every spec clause should trace forward to the code that implements it and the test that verifies it — and specs are versioned, with downstream code/tests flagged when a clause changes.
  • Cursor explores requirements and drafts an implementation plan before any code is written — and that plan gets reviewed and approved, not rubber-stamped.
  • Architecture diagrams and API/interface contracts are both generated from the same spec — one for human review, one for the agent to implement against precisely.
  • ADRs capture why a decision was made, not just what was built; SRS → SDS translation turns a business requirement into an implementable technical design.
  • Acceptance criteria are written as testable Given/When/Then clauses, and implementation only begins after a human approval gate — not on a draft.
