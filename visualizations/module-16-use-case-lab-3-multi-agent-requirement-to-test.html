§1 · Requirement Validator · 20 min

Be the Validator: classify every AC

Mark each acceptance criterion as TESTABLE, NEEDS_CLARIFICATION, or UNTESTABLE, the same way the agent will. The overall status on the right updates as you go. The Validator must never fill a gap with its own guess. It asks the requirement owner a question instead.

—
  • any UNTESTABLE → FAIL: stop and send the gaps to the requirement owner
  • any NEEDS_CLARIFICATION → NEEDS_HUMAN: the owner answers, then re-run
  • all TESTABLE → PASS: hand off to the Sequence Builder
§2 · Sequence Builder · 20 min

Fix the coverage matrix before moving on

The Builder's first draft of 02_test_sequence.json has two problems. An empty row means an AC has no scenario (a coverage gap). An empty column means a scenario covers no AC (it can't be traced, which is scope creep). Click cells to map scenarios to ACs, and move untraceable scenarios to open_issues.

The Builder decides what to test and in what order, never how. Each scenario has setup → action → expected result, and names the ACs it covers. It doesn't name test frameworks or include code. That's the Generator's job.
Checkpoint at the end of Part A: 01 and 02 both have status: PASS, and run_log.jsonl has two lines. Take the break only after that.
§3 · Test Generator · 25 min

The only agent that writes files, and only under tests/

Run the Generator with and without the write restriction. Then watch the pytest --collect-only smoke check fail, feed the error back to the Generator, and pass on correction round 1 of 2.

Least privilege means only one agent can write. If the Reviewer or the API Validator could edit tests, you could no longer tell which agent made which change.

§4 · API Validator · 20 min

A failing test isn't always the Generator's fault

The API Validator checks the tests against openapi.yaml and then runs them in the sandbox. Each failure has to be sorted into one of three types. Only test defects go back to the Generator. Sort these four failures.

🟡 Test defectThe test assumes a field or behavior that isn't in the spec. It goes back to the Generator with the spec reference, and counts as a correction round.
🔴 Product defectThe API doesn't do what its own spec or the AC says. Log it and flag it to the Reviewer and the owner. Leave the test unchanged.
⚪ EnvironmentA timeout, a 5xx error, or the sandbox is down. Retry once. If it still fails, mark it NEEDS_HUMAN.
😈 Tempting shortcut: "Just change the assertion to 404 so the suite passes."

📌 Recap

From one requirement to a test suite anyone can trace

  • The Validator fails early and cheaply. It raises clarification questions and never fills gaps with its own guesses.
  • The Builder works only from the validated requirement. Every scenario maps to an AC, and every AC has at least one scenario.
  • The Generator is the only agent that writes files, and only under tests/. Each test carries req/ac/seq markers.
  • The API Validator sorts each failure as a test, product, or environment problem. A product bug is never hidden by changing a test's assertion.
  • The Reviewer works from a fresh context and judges against the original requirement. It issues APPROVE, REQUEST_CHANGES, or ESCALATE, and a person approves the commit.
  • traceability.md and run_log.jsonl are what Modules 17–18 use to add automated gates and to re-run only the stages after a change.
